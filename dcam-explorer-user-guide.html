DCaM Explorer User Guide

Overview

The DCaM Explorer is an interactive visualization of the DCaM model found at DCaM Explorer. DCaM helps project teams and stakeholders explore and understand all of the content that comprises DCaM.

The DCaM Explorer displays high-level capabilities that group together related capabilities, giving stakeholders an overview of key behaviors.

DCaM Domains

DCaM organizes capabilities into five domains.

  • Collaboration: How stakeholders and teams work together to plan, build, and release software. Collaboration includes communication, feedback loops, and cross-functional roles within teams.
  • Development and Test: Engineering practices that produce repeatable results and ensure quality software; growing from manual, inconsistent practices to comprehensive automated practices.
  • Pipeline Management: How project teams build, verify, release, and deploy changes; growing from ad hoc scripts to standardized, versioned, and policy-governed CI/CD pipelines for reproducibility.
  • Security: How project teams integrate security throughout the development process; growing from reactive scans to continuous, automated security integrated throughout.
  • Operations: Practices that evolve from manual releases and basic monitoring to automated, reliable operations with production-monitoring, alerting, incident response and recovery.

Capability Levels

DCaM defines capability levels to measure project team behaviors and practices. DCaM allows for "spikey" maturity – different maturity levels across the domains – so project teams target needed improvements without feeling pressure to “achieve a particular level”.

  • Level 0 – Ad Hoc: Teams may not have a shared version control system, may not be practicing Agile, and may not be working with Security or Operations. Communication is ad-hoc and unstructured. Work is largely schedule based, and not goal based.
  • Level 1 – Development Foundations: Teams have a shared codebase in a central version control repository with a common understanding of the basic structure of the application and the deployable artifacts, along with a repeatable build to produce those artifacts. Security, Operations, and customer interactions exist but are not integrated.
  • Level 2 – Development Insights: Teams have a well-defined, stable product that is developed using an Agile framework. Writing and running tests is an integral part of development along with a pipeline that executes. Security and Operations work closely with the team.
  • Level 3 – Increasing Automation: Teams have a well-defined product, defined deployment target environments, operations integrated into the team, and a comprehensive set of automated tests that ensure the quality of the product.
  • Level 4 – Proactive Engineering: Teams have automated most of the software development lifecycle. Security and Operations are fully integrated in the team. Teams monitor and analyze their environment and failures, continuously improving processes and its product.
  • Level 5 – Continuous Improvement: Teams use feedback from throughout the pipeline and deployment metrics to optimize how changes flow from the team to deployment.

Browsing the Model

From the DCaM Explorer, you can see which high-level capabilities are found in which capability levels. Clicking on any of the high-level capabilities will open a side-panel that provides more details. Recall that each high-level capability may have one or more capabilities associated with it.

High Level Capability Side Panel

In the side-panel, you can view the capabilities that make up the high-level capability. For each capability, there is a description, a list of applicable functional roles, prerequisites, relevant survey questions, and external references.

  • Description explains the practices and behaviors applicable to the capability.
  • Functional Roles include a list of functional roles that are applicable to the capability.
  • Prerequisites show how different capabilities are interrelated. While hovering over a prerequisite, the high-level capabilities involved are highlighted to show where in the broader picture the pre-req applies. The high-level capability of the prerequisite is shown in black and prerequisite capabilities are shown in gray. There are a few different views.
    • Tree view – Shows the prerequisites in hierarchical order and provides an idea of what prerequisites are needed to enable successful adoption of this capability. Tree view is the default view.
    • List View – lists all the dependencies, including transitive dependencies.
  • Questions contain the associated survey questions
  • References contain links to external references that can provide additional information on the capability.

Agile Capability Model (ACaM)

From the DCaM Explorer home, click on ACAM to view the Agile only aligned capabilities.

To return to the main DCaM view, click on DCaM.

Functional Roles

From the DCaM Explorer home, you can filter on capabilities that apply to a specific role. For instance, if you are a Software Tester, you may want to view only the high-level capabilities that are applicable to you.

Select the Functional Roles drop down, and check “Software Tester”. The interactive DCaM Explorer will now display only the high-level capabilities that apply to the Software Tester functional role.

You can select more than one Functional Role, such as “Security” and “Software Tester” to view the high-level capabilities that apply to the Security or software tester functional roles.

To return to the main DCaM view, the Functional Roles drop down, uncheck “Software Tester” and check “All”.

Glossary

From the DCaM Explorer home, select Glossary to view the key terms and their meanings. The glossary is intended to build a common lexicon of key terminology and jargon that are used in DevSecOps, and highlights what they mean within the context of the model.

To return to the main DCaM view, click Explorer.
